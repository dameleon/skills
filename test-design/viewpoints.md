# 観点モデル(結合 / 外部結合)

シナリオ観点を主軸に、機能テストとしての結合観点を併せた観点カタログ。
ケース生成時に「観点 × 抽出項目(結合点・外部依存・業務フロー)」のマトリクスで網羅を計画する。
各観点に**観測ポイント**(何を観測して合否を判定するか)を付した。すべて実施者・ツール非依存で記述する。

`適用`: 結=内部結合 / 外=外部結合 / 両=両方。`--scope` で対象を絞る。

## 使い方

1. **シナリオ観点を起点**にする。1 ユースケースにつき 主→代替→例外 の順で分岐点ごとにシナリオを派生させ、全分岐点を最低1シナリオで通す(全順列ではなく蓋然性の高い経路を優先)。
2. シナリオを通す中で関与する結合点に、機能結合の観点(インターフェース契約/データ整合性/異常系/横断的関心)を当てる(技法 × 結合点のマトリクス)。
3. **ペルソナ視点で網羅を補完**する。技法ベースで漏れる利用文脈起因の欠陥を拾う。
4. 観点ごとに最低1つの確認を残す。当てられない観点は「保留/不可」に分類し理由を書く(`verification.md`)。

ペルソナ(観測点へ翻案して使う): 新人/初見、ベテラン/高頻度、悪意ある操作者、仕様懐疑、データ整合性監査、移行担当、回帰デグレ番人。

## 目次

シナリオ / インターフェース契約 / 異常系/回復性 / データ整合性 / 横断的関心 / 移行/回帰

## シナリオ(主軸)

| 観点 | 適用 | 観測ポイント |
|---|---|---|
| 正常フロー(基本系) | 両 | 事前条件成立→主アクター操作列→事後条件(DB確定状態・通知発行・後続連携)まで全て期待どおり成立するか。UI 表示で止めず多層で観測 |
| 代替フロー | 両 | 各代替分岐を別シナリオで立て、最終的に基本系と同一の事後条件へ収束するか。途中の中間状態が基本系と矛盾しないか |
| 例外フロー | 両 | 例外時に基本系へ戻らず例外事後条件で終了するか。打ち切り時点で部分コミット・中途半端な状態が残らずロールバック/補償が効くか |
| 状態遷移をまたぐ業務フロー | 両 | 申請→承認→確定等の各遷移前後で正しく遷移し、不正遷移(スキップ・逆行・二重・無効)が拒否されるか。状態をまたぐ持ち越しデータが破損しないか(N+スイッチ) |
| E2E コンポーネント協調 | 両 | 主+代替/例外を端から端まで通し、関与する全コンポーネントが規定シーケンスで協調し各段のデータ受け渡しが欠落しないか |
| ペルソナ: 新人/初見 | 両 | 案内なし・デフォルト値・未入力・標準権限のままで業務を完遂でき、途中で行き止まらないか |
| ペルソナ: ベテラン/高頻度 | 両 | 連続投入・一括処理・並行操作・キャッシュ温まり後など高負荷な使い方で結合先(DB接続・キュー・外部API)が破綻せず一貫した結果を返すか |
| ペルソナ: 悪意ある操作者 | 両 | 他者リソースID指定・権限昇格・パラメータ改ざん・想定外順序で叩いた時、認可境界とサーバ側バリデーションが結合レベルで守られるか(クライアント側だけの防御でないか) |
| ペルソナ: 仕様懐疑 | 両 | 相反しうる2要件を同時に満たす入力を与えた時、システムが一方を破綻させず明示的に拒否/優先し、両立不能が実行時に顕在化するか(「設計どおり=正しい」を疑う) |

## インターフェース契約

| 観点 | 適用 | 観測ポイント |
|---|---|---|
| パラメータ契約 | 結 | 引数の型・順序・個数・必須/任意が呼び出し先の期待と一致するか(過不足・並び違い) |
| データ形式・単位・スキーマ整合 | 両 | 送受信データの形式・文字コード・単位・スキーマ/メッセージ構造が両側で一致し、変換(JSON/XML, m/ft, 円/銭)が正しいか |
| データ前提・制約の整合 | 結 | 呼び出し先が前提とする値域・非null・参照整合・大小関係を呼び出し元が満たして渡すか(called側の事前条件をcallerが保証するか) |
| 境界値・同値分割(結合点) | 両 | 授受する値の最小/上限/直前直後・空/null/最大長/最大件数の境界と同値クラスを網羅し、呼び出し先が落ちず正しく処理するか |
| 条件組合せ(デシジョンテーブル) | 結 | 在庫・与信・権限等の複数コンポーネントにまたがる条件の組合せごとに、結合後の出力がルール(AND/OR/NOT・排他/必須)どおりか |
| 構成・パラメータ組合せ(ペアワイズ/分類木) | 両 | 複数コンポーネント・パラメータ・設定(バージョン/フラグ/環境)を2因子網羅し、結合構成ごとに動作するか |
| 呼び出しグラフ/結合構造の被覆 | 結 | コンポーネント間の全インターフェース(呼び出しエッジ)が最低1回起動され、双方向の往復経路が実行されるか(片方向だけの未検証がないか) |
| コンシューマ駆動契約 | 外 | プロバイダの現行スキーマ/応答が登録済みの全コンシューマ期待(契約)を満たし、互換性ポリシー(後方/前方/双方向)に反する変更が拒否されるか(例: Pact, スキーマレジストリ) |
| 後方/前方互換性 | 外 | 既存フィールドの削除・型変更・enum値削除・必須化が起きていないか旧スキーマで検証し、新規追加フィールドを受信側が無視して動作継続するか |
| APIバージョニング/新旧共存・廃止予告 | 外 | 並走期間に新旧両方が正しく応答し、非推奨/Sunset ヘッダが返り、切替でダウンタイムが出ないか |

## 異常系/回復性

| 観点 | 適用 | 観測ポイント |
|---|---|---|
| エラーコード/例外の伝播と処理 | 結 | 呼び出し先のエラー/例外/異常終了を呼び出し元が検知し、握り潰さず適切に処理・伝播するか |
| タイムアウト設定と発火 | 両 | 接続/読取タイムアウトが妥当値で設定され、超過時にハングせず期限内にエラー返却するか(無限待機・コネクション枯渇を起こさないか) |
| リトライ + 指数バックオフ + ジッタ | 外 | 再試行が指数バックオフ+ジッタで上限付きか、再試行可能エラー(5xx/429)のみ対象か、非冪等操作を二重実行しないか |
| サーキットブレーカ + フォールバック | 外 | closed→open→half-open の遷移としきい値、open時の即時失敗/フォールバック(キャッシュ/デフォルト/縮退)で安全側に倒れるか |
| 依存先の不在・劣化・部分応答耐性(バルクヘッド) | 両 | 相手が停止・遅延・部分応答のとき、他経路を巻き込まず(バルクヘッド)タイムアウト・リトライ・フォールバックが働くか |
| 部分失敗時の全体整合 | 両 | 複数下流のうち一部だけ失敗した時に全体整合を保ち、部分コミット/中途半端な状態を放置しないか |
| レート制限/スロットリング(429) | 外 | 429受信時に Retry-After / X-RateLimit-* を尊重して待機・再試行し、クォータ上限内に収まるか |
| デッドレターキュー(DLQ)・毒メッセージ隔離 | 外 | 最大試行超過メッセージが原因情報付きでDLQへ隔離され、無限リトライや消費停止に陥らず再処理/監視できるか |
| ネットワーク分断/障害注入下の回復と再同期 | 両 | 接続断・パケットロス・DNS失敗・partition・遅延注入下で回復し、復旧後に再同期して不整合を残さないか |
| エラー推測/探索的観点 | 両 | 結合点で頻出する欠陥(null/空/タイムアウト/重複呼び出し/順序逆転)や想定外順序・並行操作を狙い、連携が崩れる箇所を顕在化させるか |
| 異常系/負ケースの網羅 | 両 | 不正入力・認可エラー(403)・必須欠落・想定外フローの各負ケースで、システムが成功させず明示的に拒否し、副作用(部分コミット等)を残さないか |

## データ整合性

| 観点 | 適用 | 観測ポイント |
|---|---|---|
| 冪等性(idempotency key) | 両 | 同一呼び出し/同一キーの重複・再送・再実行で副作用が1回分のみ(二重課金/二重登録/残高・在庫の二重更新がない)か |
| 重複配信(at-least-once)の収束 | 外 | 同一メッセージが複数回届いても消費側(inbox/dedup)で1回処理に収束するか(exactly-once は前提とせず冪等で吸収するか) |
| メッセージ順序保証 | 外 | 順序が要るキー単位で逆順/前後到着しても整合する、または順序ずれを検知できるか(古い状態での上書きが起きないか) |
| トランザクション境界の原子性(dual-write防止) | 外 | DB更新とメッセージ発行が同一原子境界(outbox等)で行われ、片方だけ成立する(状態更新済みだがイベント未発行/逆)を作らないか |
| 結果整合性の収束と中間状態露出 | 外 | 中間不整合が許容範囲内で最終収束するか、収束前の読取で read-your-writes 違反や矛盾を見せないか |
| 補償処理(saga)の完全性 | 外 | いずれかのステップ失敗時に各先行ステップの補償が正しい逆順で完全実行され、補償漏れ/補償失敗の残留がないか |
| Outbox/Inbox 配信保証(effectively-once) | 外 | プロデューサ側outboxで取りこぼしなく発行し、コンシューマ側inboxで重複排除して effectively-once になるか |
| リコンサイル/差分検知 | 外 | 連携両端のデータを照合し、件数/金額/キーの差分(ドリフト)を検出・是正できるか |
| 参照整合性監査 | 両 | 業務完了後に関連エンティティ間の件数・合計・参照整合性(親子・外部キー・残高=明細合計)が破れず、二重計上・孤児レコードが出ていないか |

## 横断的関心

| 観点 | 適用 | 観測ポイント |
|---|---|---|
| 共有状態・同期・競合(race/deadlock) | 結 | 複数コンポーネントが共有データ/リソースへ並行アクセスする際、同期・排他・順序保証が成立し、競合・デッドロック・共有データ不整合が起きないか |
| 初期化・接続/解放のライフサイクル整合 | 結 | 初期化値・接続確立/再接続・リソース解放が両側で整合し、未初期化参照・接続リーク・解放漏れ・再接続時の状態不整合がないか |
| 呼び出し順序・前提状態 | 結 | 規定順序(初期化→処理→解放、在庫確認→決済)で呼び、順序前提が崩れた時に拒否され、初期化前呼び出し・必須前処理欠落で不正動作しないか |
| 認証トークン期限切れ/更新・認可スコープ | 外 | トークン失効(401)時に自動リフレッシュし進行中要求が回復するか、権限不足(403)・スコープ不一致で適切に拒否され越権が発生しないか |
| 文字コード/エンコーディングの境界越え | 両 | UTF-8/マルチバイト/絵文字/サロゲートペア/BOM/改行コードが境界越えで化けず、正規化(NFC/NFD)差異で不一致にならないか |
| タイムゾーン/クロックスキュー | 両 | 日時が UTC で授受され、TZ変換・DST境界・端末間時計ずれで期限/順序/集計・署名/トークン有効期限を誤判定しないか |
| 数値/日付フォーマット・精度・ロケール差 | 両 | 小数精度・通貨単位・桁区切り・日付書式・ロケール差で丸め誤差・桁あふれ・MM/DD取り違えが起きないか |
| ヌル/欠損/オプショナルの区別 | 両 | null・空文字・キー欠如・空配列を区別して扱い、必須欠損時に NPE/デフォルト誤適用/黙殺にならず明確に失敗するか |
| 境界サイズ/ペイロード上限・ページング | 外 | 最大ペイロード/巨大リスト/長大文字列/空ボディ/上限超過(413)を正しく扱い、全ページを取得しきり空/最終ページ・カーソル失効・途中追加削除に耐えるか |
| セマンティック/業務契約 | 外 | 構造検証では拾えない「いつ・どのイベントが・どの順で発火するか」の業務的期待が成立し、構造は合うが業務ロジック上の連携破綻がないか |

## 移行/回帰

| 観点 | 適用 | 観測ポイント |
|---|---|---|
| 旧データ/移行データ投入 | 両 | 旧形式・実データ相当のデータを投入した時、現行の連携が破綻せず移行後の整合(件数・キー・値域)が保たれるか。移行は「仕様どおり動く」を正解基準にする |
| デグレ波及(回帰) | 両 | 変更点の周辺機能・既存連携経路に波及がないか。既存シナリオが従来どおりの事後条件で通るか |
| 仕様と実装/挙動の突合 | 両 | 「動いているはず」を信用せず、一次情報(仕様・契約)と実挙動を突き合わせ、暗黙に変わった振る舞いを検出するか |
