# 検証ルーブリック(独立レビュー subagent 用)

生成されたテストケースを**批判的に**検証するためのチェックリスト。
Phase 3 でオーケストレータが起動する case-reviewer subagent が、これを使って粗探しする。

## レビューの原則

- **独立性**: 設計者の意図・思考過程を推測しない。`CASES{ext}` と `PLAN.md`・Test Basis(一次情報)だけを根拠に判定する。独立性の本質は「生成時の思考過程を参照しない fresh なパス」であること。別 subagent(fork)が第一手段だが、dispatch できない環境では、生成根拠を見ずに `CASES{ext}`+`PLAN.md`+Test Basis だけを再読する別パスで代替してよい(自己レビューに退行しない限り独立性は保たれる)。
- **批判的**: 「動いているはず」を信用しない。曖昧・未検証・実施者依存を疑い、合格に倒さず指摘する。
- **オラクル独立**: コードそのものを正解の根拠(オラクル)にしない。期待結果は要件/契約という独立した根拠源から導けているかを見る。
- 各 finding に `ケースID` / `違反したチェック項目` / `重大度(blocker|major|minor)` / `分類(修正可|要仕様判断)` / `具体修正案` を付け、`REVIEW.md` に出力する。問題が無ければ空で返す。
- `分類`: 修正でケースを直せるものは `修正可`、一次情報の欠落や真の仕様曖昧で確認が要るものは `要仕様判断`。オーケストレータはこの分類で処理を分ける(下記)。

## チェック項目

### blocker(これがあると生成完了にできない)

| # | チェック | NG 例 |
|---|---|---|
| B1 | 各ケースが Test Basis(要件ID/仕様書セクション/API契約/受入条件)へ前方トレース可能で、参照先が URL・章番号・ID で特定できる形か | 期待結果の出典が「たぶんこういう仕様のはず」で、参照すべき仕様IDやドキュメント箇所が一切示されていない |
| B2 | 期待結果・カバレッジ判定に信頼度ラベル(検証済/推論/仮定)が付き、仕様未確定箇所が断定で書かれず「不明」が明示されているか | 仕様未確定の項目を、推論にすぎないのに「仕様どおり201を返すこと(検証済)」と断定し、確認待ち(仮定)であることを隠している |
| B3 | 各ケースに、判断の余地なく合否を判定できる具体的な期待結果(値・状態・ステータスコード等)があるか。期待結果は「観測可能な副作用集合(DB行・発行イベント・外部呼び出し・状態)」と「応答コード/値」に分けて評価する。前者が判断余地なく書けていれば B3 充足。後者のみ一次情報欠落なら、ケース全体を不可とせず当該フィールドだけ保留+OQ(信頼度=仮定)にしてよい | 期待結果が「正しく処理される」「正常に表示される」だけで、201か200か、ボディに何が含まれるか不明で誰が見ても同じ結論にならない |
| B4 | 期待結果が外部から観測可能な出力(レスポンス・DB確定値・発行イベント・ログ・連携先到達)に紐づき、何を根拠に正解と判定するか(オラクル)が示されているか。UI 表示だけで判定していないか | 「内部キャッシュが更新されること」を期待結果にしているが観測手段が定義されていない、または操作後を UI 表示だけで判定し DB確定・通知・連携を観測していない |

### major(自動修正対象。観点漏れ・曖昧・実施者依存)

| # | チェック | NG 例 |
|---|---|---|
| M1 | 各観点が「テスト可/保留(情報待ち)/不可(対象外、または環境・権限・オラクル不在で検証不能)」に分類され、保留・不可に理由と必要情報があるか | 管理者権限やログアクセスが無く実際は検証不能な観点を、無印で「テスト可」に混ぜている |
| M2 | 正常系だけでなく異常系/負ケース(不正入力・認可エラー・必須欠落・想定外フロー)が設計され、happy path bias に陥っていないか | 外部連携APIで200系の成功ケースしか無く、不正トークン・必須欠落・権限不足時の振る舞いが一切検証されていない |
| M3 | 外部結合固有の障害(タイムアウト・部分停止・破損ペイロード・遅延・リトライ・冪等性)への振る舞いが設計されているか | 外部決済ゲートウェイ連携で、応答タイムアウト時の挙動(リトライ/二重課金防止/通知)を検証するケースが無い |
| M4 | 結合点で授受されるデータの形式・型・スキーマ整合と API 契約(必須フィールド・ステータス)が検証され、各サービス内部の動作確認だけで終わっていないか | 結合テストなのに各サービス内部の動作だけ確認し、Aが渡す JSON と Bが期待するスキーマの不一致(余分フィールド/型違い)を検証していない |
| M5 | 対象要件・インターフェースが過不足なくケースに対応づくか(前方: 全要件にケース有/後方: 各ケースが要件に紐づく)。未カバー要件と孤児ケースを洗い出せるか | 仕様にある「決済失敗時のロールバック要件」に対応するケースが1本も無い、または逆にどの要件にも紐づかないケースが残っている |
| M6 | 境界値(下限直前/下限/上限/上限直後)と同値クラスが、結合点で授受されるデータに網羅されているか | 件数上限100のバッチ連携で、99/100/101 の境界を試さず「10件」など中央値だけで合格としている |
| M7 | 1ケース=1検証目的に絞られ(setup/cleanup除き目安10-15ステップ以内)、複数の独立検証を1ケースに詰め込んで失敗原因の切り分けが不能になっていないか | 「注文APIを呼び、在庫DBを更新し、メール送信し、監査ログも検証」が1ケースで、どこで落ちたか特定できない |
| M8 | 各ケースが他ケースの実行結果・順序・共有状態に依存せず、単独でも任意順でも成立するか(本質的に順序を持つ業務は前段を setup/fixture で再現する意図的依存に変換しているか) | ケースBが「ケースAが先に作ったユーザID=100」を前提にし、Aをスキップ/並列実行すると落ちる |
| M9 | 入力・時刻・乱数・外部応答などの非決定要因が固定/制御され、同じ手順なら毎回同じ結果になるか(フレーキーでないか) | 期限を「今日の日付」、IDを「ランダム生成」のままにし、実行日や乱数次第で合否が変わる |
| M10 | 実行前に成立すべき前提条件(初期データ・依存サービス稼働・認証状態・フラグ)が漏れなく明記され、前提崩れを fail-fast で検知するか | 「カートに商品がある状態で決済」なのにカートへの商品投入(前提データ)が記載されず、空カートで別経路に落ちる |
| M11 | 実行後の最終状態と後始末(作成データ削除・状態リセット・トランザクション戻し)が定義され、状態リークで後続を汚染しないか | 外部システムにレコードを作るケースで後始末がなく、再実行時に「重複キー」で失敗する |
| M12 | 特定の自動化ツール・実行環境・個人の暗黙知に依存せず、観点と期待結果が抽象的に書かれ誰/どの環境でも同じ検証ができるか(Local Hero 回避)。なお「外部系を○○状態にする」等の setup/前提条件の記述は実施者依存ではない(禁止は特定ツール名・UI セレクタ・個人マシン前提) | 期待結果が「自分のローカルの postman コレクションを流すと緑になる」など特定ツール・特定マシン前提 |
| M13 | 対象を知らない第三者でも追加質問なしに実行できる入力値・操作手順・データ(エンドポイント・必須パラメータ・サンプル値)が具体的に揃っているか | 「APIを正しいパラメータで呼ぶ」とだけ書かれ、エンドポイント・必須パラメータ・サンプル値が無く実行者ごとに解釈が割れる |
| M14 | 代替フローは基本系と同一の事後条件へ収束し、例外フローは基本系へ戻らず例外事後条件で終了して部分コミット/中途半端な状態を残さないか | 例外フローのケースが、打ち切り後にロールバック/補償の確認をせず状態が更新されたまま放置されるのを見逃している |

### minor(安価なら適用、他は備考)

| # | チェック | NG 例 |
|---|---|---|
| m1 | 各ケースが一意の ID を持ち、目的・入力・観点が実質重複していないか | 「正常にログインできること」が ID 違いで3本あり入力も期待結果も同一 |
| m2 | 冪等性・順序・配信保証で exactly-once を前提に置かず、at-least-once + 冪等処理による effectively-once として検証対象を立てているか | メッセージ連携で「重複は来ない前提」とし、重複配信時に消費側で1回処理へ収束するかの観点が欠落 |

## カバレッジ検証(ケース横断)

個別ケースに加え、集合として次を確認する。
- **観点マトリクス**: `viewpoints.md` の観点グループごとにケースが最低1つあるか。空のグループは「保留/不可」の理由が `PLAN.md` にあるか。
- **双方向トレーサビリティ(RTM)**: 前方(全要件→ケース有)と後方(各ケース→要件紐づき)で突合し、未カバー要件と孤児ケースを列挙する。
- **scope/style 整合**: `--scope`/`--style` の指定に対し、外部結合観点・シナリオ観点の比重が指定どおりか。

## 重大度 → アクション(オーケストレータが Phase 4 で適用)

処理は `分類` を先に見て分ける。

| 分類 / 重大度 | アクション |
|---|---|
| 修正可 / blocker | 自動修正。2 周(Verify 最大3回)後も残れば完了せず停止し、サマリ冒頭で未解決 blocker として明示報告する(「保留」に格下げして出力しない) |
| 修正可 / major | 自動修正(該当ケース修正、または designer を findings 付きで再 dispatch) |
| 修正可 / minor | 安価なら適用、高コストなら備考に残す |
| 要仕様判断(真の仕様曖昧・一次情報欠落) | 捏造せず該当ケースを「保留」+ Open Question 化。`--gate review/approve` では停止して確認 |

**早期収束**: ある周で修正可の finding がすべて解消し、残りが要仕様判断のみになったら、最大2周を待たず収束として打ち切る(一次情報が無いと直せないため追加 Verify は無駄)。

## finding 出力フォーマット(REVIEW.md)

```markdown
## 検証 findings
<!-- 各行: [チェック項目ID][分類] ケースID: 問題 → 修正案 -->

### blocker
- [B3][修正可] TC-002: 期待結果が「正常に処理される」で観測ポイント不明 → 「503 を返し orders 行が増えないこと」に具体化する
- [B1][要仕様判断] TC-007: 期待ステータスの出典が不明(仕様に記載なし) → 一次情報を確認するまで保留 + Open Question 化

### major
- [M2][修正可] (全体): 外部在庫API の異常系ケースが無い(happy path bias) → タイムアウト/403/必須欠落のケースを追加

### minor
- [m1][修正可] TC-005/TC-008: 目的が重複 → 統合 or 観点を差別化

## カバレッジ
- 未カバー観点グループ: データ整合性(冪等性のケースが無い)
- 孤児ケース: なし / 未カバー要件: REQ-ORD-012(ロールバック)
```
