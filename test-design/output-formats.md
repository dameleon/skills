# 出力形式リファレンス

入力(対象)も出力(形式)も任意指定が前提。すべての形式は下記の**正準ケーススキーマ**から写像する。
組み込み形式(`md`/`csv`/`gherkin`)を既定で持ち、任意指定があればそれに従う。

## 正準ケーススキーマ

形式に依存しない内部表現。1 ケース = 以下のフィールド。

| フィールド | 説明 |
|---|---|
| `id` | 一意なケースID(例 `TC-001`)。シナリオの枝番は `TC-001-a` 等 |
| `group` | 観点グループ(`viewpoints.md` の見出し。例: シナリオ、インターフェース契約、異常系/回復性) |
| `viewpoint` | 具体観点(例: タイムアウト時のリトライ、必須項目欠落) |
| `level` | `結合` / `外部結合` |
| `title` | シナリオ名・ケースタイトル |
| `precondition` | 前提条件(初期状態・データ・外部系のスタブ/モック状態・認証状態など) |
| `steps` | 手順。**実施者・ツール非依存**。「誰が」「何のツールで」を書かず、システムへの入力と操作を時系列で |
| `test_data` | 入力値・境界値・異常値。具体値で |
| `expected` | 期待結果 + **観測ポイント**。観測可能なシステム出力で表す(API 応答コード/本文、DB 行、キュー/トピックのメッセージ、ログ、ファイル、画面表示など) |
| `test_basis` | 一次情報参照。仕様の節見出し、チケット番号、`[REF: path:line]`。**期待値の導出元が SUT 自身にならないようにする**: 仕様側の一次情報(設計ドキュメント・デザインファイル・受入条件・API 契約)を必ず 1 つ以上引き、実装参照はその裏取りとして併用する。実装参照だけで埋めたケースは「実装が仕様どおりか」ではなく「実装が実装どおりか」しか検証しない |
| `confidence` | 🟢 VERIFIED(一次情報/コードで確認済) / 🟡 INFERRED(妥当な推論) / 🔴 ASSUMED(仮定)。ケース全体は1ラベルで、最弱のサブ表明に合わせる。期待結果のフィールド間で信頼度が異なる場合(例: 副作用は確認済だが応答コードは仮定)は、その差を `notes` に書く |
| `coverage` | テスト可 / 保留(要確認) / 不可(対象外、または環境・権限・オラクル不在で検証不能。理由必須) |
| `notes` | 備考・未確認事項(Open Question) |

### 実施者非依存の書き方(重要)

- 良い手順: 「注文確定 API に有効なカートIDで POST する」「在庫サービスを応答遅延 5s に設定する」
- 悪い手順: 「Cypress で確定ボタンをクリック」「テストを実行して green を確認」(ツール/実施者依存)
- 良い期待: 「`POST /orders` が 201 と `orderId` を返し、`orders` 行が 1 件増え、`order.created` がキューに 1 件入る」
- 悪い期待: 「正常に登録される」「テストがパスする」(観測ポイントが不明)
- 「在庫サービスを応答遅延 5s にする」のような外部系の状態設定(setup)を前提条件・手順に書くのは許容する(観測可能な状態宣言であり実施者非依存)。禁止は特定ツール名・UI セレクタ・個人マシン前提のみ

## 組み込み形式

`--output` の値と拡張子・写経元テンプレの対応(dispatch 時に `{ext}`/`{template}` として渡す):

| `--output` | 拡張子 `{ext}` | 写経元テンプレ `{template}` |
|---|---|---|
| `md`(既定) | `.md` | `templates/cases.md` |
| `csv` | `.csv` | `templates/cases.csv` |
| `gherkin` | `.feature` | `templates/cases.feature` |

### md(既定): Markdown 表 — `templates/cases.md`

人が読みやすい一覧。ケース表 + カバレッジサマリ。列は正準スキーマに対応。

### csv: セミコロン区切り CSV(ISO/IEC 25010 対応列) — `templates/cases.csv`

スプレッドシート/課題管理へ取り込む用。参考事例の列ずれ防止規約を踏襲する。

- **区切り文字はセミコロン `;`**(セル内のカンマと衝突させない)
- **セル内改行は `<br>`** に統一(生の改行を入れない)。セル内で複数値を並べる場合もカンマ等を使い `;` を入れない(列ずれ防止)
- **UTF-8 固定**、ヘッダ行必須。全行のフィールド数をヘッダと一致させる(`awk -F';' '{print NF}'` で検算)
- 品質特性列は **ISO/IEC 25010** から選ぶ: 機能適合性 / 性能効率性 / 互換性 / 使用性 / 信頼性 / セキュリティ / 保守性 / 移植性。結合・外部結合では特に「機能適合性」「信頼性」「互換性」「セキュリティ」が中心になりやすい。**主たる1特性**を入れ、副次特性は Notes に記す
- 正準スキーマの単一フィールド `expected`(期待結果 + 観測ポイント)は、CSV では `Expected`(期待結果)と `VerificationPoint`(観測ポイント)の **2列に分割** して写像する
- 列: `TestCaseID;RequirementID;Level;QualityCharacteristic;Group;Viewpoint;Title;Precondition;Steps;TestData;Expected;VerificationPoint;TestBasis;Confidence;Coverage;Notes`

### gherkin: Feature/Scenario — `templates/cases.feature`

BDD ツールに載せやすく、Gherkin は本来実施者非依存。
- `Feature` = 対象機能/連携、`Scenario` または `Scenario Outline`(データ駆動は `Examples`)
- `Given`(前提条件)/ `When`(手順)/ `Then`(期待結果 + 観測ポイント)
- タグで観点を表現: `@external @resilience @timeout`、`@scenario`、`@regression`
- Test Basis・信頼度・カバレッジは `#` コメントで各 Scenario の直前に付す

## 任意形式の扱い

`--output` がパスまたは自由記述のとき:
1. 指定サンプル/テンプレを読み、その構造(列・見出し・粒度)に正準フィールドを写像する。
2. 既存ファイルに追記する場合はヘッダ/列順を保ち、列ずれを起こさない。
3. **トレーサビリティ・信頼度・カバレッジの受け皿が無い形式**でも捨てない。追加列/コメント/末尾の補足表として残し、欠落する場合はサマリで「この形式では X を表現できない」と明示する。
4. 区切り・エンコーディング・改行規約が指定にあればそれを優先(無ければ CSV 既定に従う)。
5. **正準ケースID を保持する**。指定形式が独自のID列(例: `No`)を持つ場合でも、正準ID(`TC-xxx`)を列か備考に残し、要件↔ケースの双方向トレーサビリティを切らさない。
6. **区切り衝突を防ぐ**。カンマ区切りの任意CSVでは、区切りと衝突しうるセルを RFC4180 でクオートし、セル内に生のカンマ/改行を残さない。出力後は `awk -F,` ではなく実 CSV パーサでフィールド数を検算する。
7. **正準に対応の無い列を埋める**。指定形式に正準スキーマへ対応の無い列(例: `優先度`)があれば、既存シグナル(重大度/`[critical]` 性 等)から導出して埋め、導出規則を備考かサマリに明記する。空欄にしない。

## アーティファクト管理(任意・大規模運用向け)

継続運用するなら参考事例の二層管理を採れる(必須ではない)。
- `master/<機能>.<ext>`: 生きた正本。使わなくなったケースは削除せず `DEPRECATED` と注記して履歴を残す。
- `artifacts/YYYY-MM/`: 課題ごとのスナップショット。遡及可能性を確保。
