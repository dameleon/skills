# Reference: memory-gc

## 種別判定のシグナル

| 種別 | シグナル | 例 |
|---|---|---|
| **rule** | 命令形・禁止形（「〜すること」「〜しない」「必ず〜」）。読み手の行動を変えることが目的 | 「PR の base branch は派生元にする」「steep check はスキップする」 |
| **knowledge** | 過去形・事実の記述。決定事項・設計判断・仕様。日付や issue/PR 番号を伴うことが多い | 「KAG-213 でマスタ化設計を採用した」「OPEN-3: 鮮度は最新必須と確定」 |
| **tips** | 障害事象 + 対処のペア。「〜で失敗する」「対処: 〜」の形 | 「新規 worktree で GemNotFound → bundle install で解消」 |

境界ケース: 「tips が命令形で書かれている」ことが多い（例:「steep はスキップする**こと**」）。
事象の説明が主なら tips、事象抜きで行動だけ指示しているなら rule と判定する。

## 陳腐化検証の実例（2026-06-10 GC で実証）

実測可能な主張は推測せず必ず実行して確かめる。無害な確認コマンドの例:

| メモリの主張 | 検証コマンド（読み取り専用） | 結果 |
|---|---|---|
| 「Bash で `$()` は承認が要る」 | `echo "x=$(whoami)"` を実行（承認の有無は UI の目視でなく、コマンドが中断なく結果を返したかで判別する） | この環境では承認なしで通った → **破棄（環境条件付き）として提案** |
| 「`<` リダイレクトは承認が要る」 | `cat < /dev/null` を実行 | 同上 → 破棄（環境条件付き） |
| 「heredoc は auto mode で通る」 | heredoc を実行 | 成立 → ただし settings の旧 workaround 指示と矛盾していたため矛盾解消が必要だった |
| 「ツール X はパス Y にある」 | `command -v X` / `ls Y` | — |
| 「設定 Z が必要」 | `jq '.Z' ~/.claude/settings.json` | — |

検証で「状態を変える」コマンド（インストール、設定書き換え、ネットワーク書き込み）は使わない。
検証できず確信も持てないものは stale「候補」として提案表に出し、判断をユーザーに委ねる。

実行環境の構成（settings / sandbox / permission mode）に依存する検証は、結果が環境ごとに変わりうる。
判定には「この環境では」と環境条件を付記し、環境非依存の事実として断定しない。
このカテゴリの検証結果のみを根拠とする破棄は、判定先を必ず「破棄（環境条件付き）」に固定する（無条件破棄にしない）。
また、主張の対象リポジトリが現環境に存在しない場合、repo 依存の主張は「検証不能」として扱い、それだけを理由に stale 候補にしない。

## 分類の詳細基準

### 昇格（~/.claude/CLAUDE.md）の判定

- **2つ以上のプロジェクトで独立に同じ教訓が出現**していることが最も強い根拠（例: 「plan にブランチ作成手順を含める」が atman と virginia で別々に記録されていた）
- 1プロジェクトでしか出ていなくても、内容がプロジェクト非依存（ツールの一般挙動、ユーザーの普遍的好み）なら昇格候補
- 昇格時は既存の CLAUDE.md 記述と統合し、同じことを2箇所に書かない

### 移管（CLAUDE.local.md）の判定と運用

- 命令形のプロジェクト固有ルールは原則すべて移管対象。メモリに残った rule は「弱い但し書き付きの強い命令」として注入され、プロジェクトの正規ルールを上書きする事故を起こす
- 移管先はリポジトリ**直下**の `CLAUDE.local.md`（公式サポートの個人用・自動ロード・git 管理外ファイル）
- **untracked のまま置く**。tracked の `.gitignore` を編集すると diff が出るため、無音にしたければ `.git/info/exclude` に追記する
- worktree には自動で付いてこない。worktree 運用の多いリポジトリではその旨をファイル冒頭に注記する
- 移管元のメモリファイルは破棄する（二重ソース化の防止）。Why の詳細が惜しい場合は CLAUDE.local.md 側に1行で要約して載せる

### 破棄の判定

- 陳腐化が実測で確認されたもの
- 上位層（CLAUDE.md / CLAUDE.local.md / settings.json）と重複・矛盾し、上位層が正のもの
- 終了済み案件の進行メモで、決定事項がすでに正規ドキュメント（リポジトリの docs 等）に反映済みのもの
- **進行中案件の知識は破棄しない**。正規ドキュメントへの移設を提案する（例: 検討中アーキテクチャの確定事項は対象リポジトリの docs へ）

## 索引ファイルの書式

### 各プロジェクトの memory/MEMORY.md

```markdown
# Memory

## <カテゴリ>（例: プロジェクト知識 / 開発Tips）
- [タイトル](./ファイル名.md) — 1行要約
```

- 索引は残存ファイルと1:1で一致させる（索引にだけある行・実体にだけあるファイルを作らない）
- 自動ロードは MEMORY.md の先頭 200 行 / 25KB まで。これに近づいたら GC のトリガー

横断インデックス（`~/.claude/memory-index.md`）と破棄履歴は作らない。自動ロードされず読まれる場面がないため、索引は各プロジェクトの `MEMORY.md` に一本化する。

## GC 実行の推奨タイミング

- 月1回程度の定期実行
- いずれかの MEMORY.md が自動ロード上限（200行 / 25KB）に近づいたとき
- メモリとプロジェクトルールの矛盾に気づいたとき（その場で部分 GC してよい）
